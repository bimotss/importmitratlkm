# Sinkronisasi COD 2026 tanpa mengubah kolom

Alur: **34 file mitra → Rekap Mitra FO dan RADIO 2026 → COD 2026**. File Rekap Mitra tetap diperbarui seperti sebelumnya. Sinkronisasi COD membaca file Rekap yang sudah dibuat; tidak membaca ulang file asli masing-masing mitra.

Untuk agent CLI di server, gunakan [instruksi deployment ini](PROMPT-AGENT-COD.md).

Profil sudah diisi berdasarkan pemeriksaan langsung:

| Tab di COD 2026 | Jumlah kolom tetap | Cara pembaruan |
| --- | ---: | --- |
| Data TIF FO | 104 (A:CZ) | Isi B:AQ diperbarui berdasarkan judul; BL, BS, BY, CA, CJ menerima data mitra/sumber yang sebelumnya memakai tumpukan tab lama. |
| Data TIF Radio | 89 (A:CK) | Isi A:BH serta BX:BY diperbarui berdasarkan judul. |
| DataDisatukan | 60 (A:BH) | Rumus penggabungan yang sudah ada di baris 1 tetap dipakai; kolom tambahan W:X diselaraskan dengan identitas barisnya. |

Tidak ada header yang ditulis ulang, kolom dihapus/ditambah/dipindah, tab diganti nama, atau sheet ID diganti. Format, validasi, dan rumus bantu yang berada di luar kolom input tetap dipertahankan. Baris boleh ditambah bila data terbaru tidak muat.

Sumber COD adalah file Rekap Mitra `1S9N054PUATRPPFpAVuZoAuKgBCmuNEYfLuUuCM8c-64` yang ditetapkan dalam `source_spreadsheet_id` di profil. Pembacaan memakai 34 tab mitra di DALAM file itu agar field tambahan COD (misalnya REG dan nomor activation) yang tidak muncul di ringkasan 51/57 kolom tidak hilang. Timestamp refresh rekap diperiksa sebelum/sesudah membaca; jika berubah, sinkronisasi dibatalkan dan dapat dicoba lagi.

Kolom sumber yang tidak ada dikosongkan; nama/judul kolom COD tetap sama. Khusus kolom REG pada FO, nilai REG sumber diutamakan, dengan REGIONAL TIF sebagai fallback. `Jarak FO` menerima field sepadan `Jarak WO`. Radio `Tanggal Awal Order` menerima `Progress Cut Off` mengikuti posisi/isi sumber yang sebelumnya dipakai.

## Identitas baris dan rumus

- FO dipadankan dengan SITE ID + SP + MITRA; RADIO dengan HOP + SP + MITRA. Tanda baca/spasi dan kapitalisasi dinormalisasi untuk pemadanan. Kunci ganda ditangani berurutan, tidak ditimpa menjadi satu record.
- Pada tahap staging, identitas lama dipadankan terlebih dahulu agar catatan/manual/helper tidak tertukar antar-site; data baru ditambahkan setelahnya. Setelah input diperbarui, slot kosong di tengah tabel dihapus sebagai baris native utuh. Catatan, format, validasi, dan rumus pada baris site yang masih aktif ikut berpindah bersama datanya, dan referensi Google Sheets menyesuaikan. Anchor rumus spill di baris 2 dipulihkan bila baris pertama dihapus. Filter dibatasi ke record aktif; validasi akhir menolak Site ID kosong di dalam data aktif.
- Rumus DataDisatukan yang sudah ada menyaring slot kosong. Identitas `test` dan `__PowerAppsId__` di W:X dipertahankan berdasarkan SITE ID + SP + MITRA, bukan nomor baris.
- Rumus bantu per baris yang aman diperluas untuk baris baru memakai native formula copy. Tidak otomatis memperluas rumus GEMINI/AI atau IMPORTRANGE per sel. Rumus spill ARRAYFORMULA/LET/MAP tetap memakai anchor yang sudah ada.
- Jika judul, sheet ID, atau jumlah kolom berbeda dari profil, sinkronisasi berhenti. Jika kurang dari setengah identitas unik lama cocok, berhenti untuk review. Jika W:X mengandung formula, berhenti agar formula tersebut tidak dipindah sembarangan.
- Kolom helper yang memang sudah menghasilkan `#N/A` dari lookup lain tidak diperbaiki oleh mode ini. Tab pendukung seperti Data DWS/JPP/Dumi/Loker tidak disentuh.

## Periksa dahulu tanpa menulis

Jalankan dengan folder kerja `/opt/import-mitra`, menggunakan user service:

```bash
cd /opt/import-mitra
sudo -u importmitra .venv/bin/python -m import_mitra sync-cod --dry-run
```

Hasil menampilkan jumlah baris, identitas lama yang tetap, tambahan, yang hilang, dan field sumber yang tidak tersedia. `dry_run: true` menjamin tidak ada penulisan sel COD atau pembuatan staging/backup. Status job lokal tetap diperbarui.

Validasi awal 11 November 2026 menunjukkan FO 6.875 dan RADIO 1.695, total 8.570; 647 tambahan FO dan 119 tambahan RADIO. Ada 1 baris FO dan 3 baris RADIO lama yang tidak cocok dan slotnya akan dikosongkan. Jumlah ini dapat berubah mengikuti sumber terbaru.

## Jalankan satu kali

```bash
sudo -u importmitra .venv/bin/python -m import_mitra sync-cod
```

Perintah memakai lock yang sama dengan refresh rekap. Tidak bisa berjalan bersamaan dengan `once` atau job otomatis.

Sebelum menulis, backup semua sel yang diisi langsung/formula pada tiga tab disimpan di `runtime/cod-backups/*.jsonl.gz`, permission 600. Snapshot juga berisi metadata/profil asli. Format umum dipertahankan. Khusus Data TIF FO Q/R memakai angka, S persen, dan V teks untuk memperbaiki format tanggal lama yang salah. Default menyimpan 24 backup lengkap terbaru; atur `MITRA_COD_BACKUP_KEEP` bila perlu. Backup berisi data/formula pribadi, jangan masukkan ke Git atau kirim tanpa disamarkan.

Pembaruan input dilakukan melalui staging tersembunyi dan satu commit batch atomik. Staging dihapus setelah selesai. Setelah commit, script memeriksa header dan merekonsiliasi jumlah SITE ID FO, RADIO, dan DataDisatukan. Jangan menganggap selesai sebelum hasilnya sukses.

## Ikut diperbarui setiap jam

Setelah sinkronisasi pertama berhasil, tambahkan pada `.env` (gunakan `sudo nano .env` bila owner root):

```dotenv
MITRA_SYNC_COD=true
MITRA_COD_PROFILE=config/cod2026.json
MITRA_COD_BACKUP_KEEP=24
```

Lalu:

```bash
sudo systemctl restart import-mitra
```

Setiap refresh rekap, termasuk tombol dashboard dan `once`, akan dilanjutkan dengan membaca hasil yang sudah tersimpan di file Rekap, lalu menyinkronkan COD. `sync-cod` manual hanya membaca file Rekap yang terakhir berhasil diperbarui, bukan file asli mitra. DataDisatukan di COD tetap memakai rumus penggabungan lama dari dua tab COD yang baru diperbarui. Tidak perlu menambah cron, service, atau trigger Apps Script.

Jika COD gagal, hasil rekap yang sudah selesai ditulis tetap tersedia, tetapi job keseluruhan berstatus gagal dan mencatat error COD. Periksa `runtime/status.json` / journal. Jangan mengubah profil untuk melewati pengecekan header tanpa menginspeksi perubahan kolom terlebih dahulu.

Nonaktifkan hanya penulis lama yang menimpa tiga tab tujuan ini jika ada. Importer tab pendukung COD boleh tetap berjalan, selama tidak menimpa input tiga tab tersebut. Service PM2, SSH, aplikasi lain, dan tab COD lain tidak perlu dihentikan.

Untuk menonaktifkan sinkronisasi COD saja, set `MITRA_SYNC_COD=false` dan restart service import-mitra. Isi COD terakhir tetap ada; file rekap masih diperbarui seperti biasa.

## Flagging di Rekap

DataDisatukan Rekap memuat 19 kolom, dengan `FLAGGING FO/RADIO` di N sebelum `KETERANGAN UPDATE` di O. FO memakai STATUS VERIFIKASI COD (termasuk alias Grouping Progress); Radio memakai Flagging Progress. Label disetarakan mengikuti SWITCH COD di FO BK dan Radio CJ, misalnya Radio 06.RFS menjadi 08.RFS. Nilai sumber kosong tetap kosong; label baru yang belum dikenal dipertahankan agar tidak hilang. Ini sengaja tidak menyalin fallback COD ke kolom lain pada label yang tidak cocok.

DataDisatukan COD tetap memakai rumus K1 yang menggabungkan FO BK dan Radio CJ, bukan langsung FO V atau Radio AU. Tidak ada perubahan struktur atau rumus COD.

## HOP Radio di DataDisatukan

Atas permintaan pengguna, Rekap menambahkan HOP di E, tepat setelah SITE ID di D. Kolom ini berasal dari HOP Radio; FO kosong. DataDisatukan COD menambahkan satu kolom paling kanan BG (kolom ke-59), berjudul HOP. Rumus BG1 menggabungkan nilai kosong untuk FO dan Data TIF Radio J2:J, disaring dengan kunci yang sama seperti A1 agar urutannya tetap sesuai termasuk slot kosong. Kolom A:BF, identitas W:X, dan rumus lama dipertahankan. Profil COD diperbarui menjadi 104/89/59; penambahan ini merupakan perubahan struktur yang diminta pengguna.

## Perubahan header TA

TA memakai `SUBSTATUS` sebagai `STATUS VERIFIKASI COD`; `STATUS` tetap merupakan progress operasional TA. Alias ini dibatasi pada sumber TA melalui `header_aliases` di konfigurasi. `required_headers` menghentikan impor sebelum penulisan jika kolom status wajib hilang, sehingga perubahan judul tidak diam-diam mengosongkan status. Nilai sumber yang kosong tetap kosong. Alias dipakai baik saat membaca file mitra asli maupun tab TA di Rekap untuk sinkronisasi COD.

Batas kapasitas workbook mengikuti 20 juta sel sejak rilis Google Sheets September 2026; pemeriksaan staging menghitung seluruh tab, staging, dan pertumbuhan grid.


## Aging order 2026

Aging dihitung di Python untuk Rekap (Aging Progress dan Grouping Aging Progress), FO COD CJ/Aging,
dan Radio COD AY/Tanggal Ganti Flagging, AZ/Aging Days, BA/Grouping Aging Progress.
FO memakai STATUS VERIFIKASI COD; Radio memakai Flagging Progress. Identitas mengikuti SITE ID/HOP + SP + MITRA.
Status yang berubah mereset aging ke 0 pada tanggal terdeteksi (WIB); status tetap bertambah sesuai hari kalender.
Order yang eksplisit di luar 2026 atau status kosong/error menghasilkan aging kosong. Tanpa indikator tahun,
order dianggap 2026 karena workbook berlingkup 2026.

Saat belum ada riwayat, Radio memakai tanggal ganti flagging sumber yang valid; FO memakai tanggal milestone
survey/perizinan/material/instalasi yang sesuai status. Fallback berikutnya tanggal inhand/order diterima,
lalu tanggal refresh. Angka awal dengan fallback inhand bukan bukti tanggal perubahan status historis.

Riwayat disimpan atomik di `runtime/aging-state.json` setelah publikasi berhasil, dengan permission 600.
Rekap dan COD memakai riwayat dan aturan hitung yang sama; tab mentah mitra tetap mempertahankan nilai sumber.
Dry-run tidak menyimpan riwayat. Kerusakan riwayat atau kegagalan menyimpan membuat job gagal agar tanggal
milestone tidak diam-diam direset. Pertahankan file ini saat update/restart atau migrasi VPS; backup bersama
runtime. Jangan menghapusnya untuk mengatasi error tanpa memeriksa penyebabnya.

Jika kunci SITE ID/HOP + SP + MITRA berulang dalam satu sumber, riwayat dipisah berdasarkan urutan
kemunculannya, sama seperti antrean identitas duplikat COD. Status berbeda pada dua kemunculan tidak
mereset riwayat satu sama lain. Kunci riwayat lama yang pernah menggabungkan duplikat tidak dipakai
untuk menginisialisasi kedua record; tanggal awal dibaca kembali dari sumber. Karena sumber tidak
menyediakan ID unik untuk membedakan duplikat, pemadanan antar-refresh mengikuti urutan sumber.


## Aging di DataDisatukan COD

Kolom paling kanan BH berjudul `Aging`, dalam satuan hari. Rumus spill BH1 menggabungkan FO CJ/Aging
dan Radio AZ/Aging Days dengan urutan/filter yang sama seperti A1: FO B:B lalu Radio K2:K sebagai kunci.
Nilai kosong tetap kosong dan nilai 0 tetap 0. Tidak memakai lookup SITE ID tunggal, sehingga link Radio
atau order berkunci sama tetap mengikuti urutan kemunculan masing-masing. BH dikelola oleh rumus native,
bukan kolom input importer; profil COD menjadi 104/89/60 dan rumus dipertahankan pada refresh berikutnya.

Rumus BH1:

```gs
=LET(kunci;VSTACK('Data TIF FO'!B:B;'Data TIF Radio'!K2:K);nilai;VSTACK(ARRAYFORMULA(IF('Data TIF FO'!CJ:CJ="";"";'Data TIF FO'!CJ:CJ));ARRAYFORMULA(IF('Data TIF Radio'!AZ2:AZ="";"";'Data TIF Radio'!AZ2:AZ)));FILTER(nilai;kunci<>""))
```
